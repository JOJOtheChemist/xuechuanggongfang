# 2026-05-28 后端筛选版下一步动作与 ES 取舍建议

## 1. 先给结论

基于本次真实接口压测结果，当前这套：

- `PostgreSQL 结构化筛选`
- `Redis 热点结果缓存`
- `后端分页返回`

已经可以作为查分系统的主方案继续推进。

现在最值得做的不是马上把主查询链路切到 Elasticsearch，而是先把下面两件事补完整：

1. `真实接口压测常态化`
2. `慢查询看板 + 冷启动预热`

原因很直接：

- 热请求已经明显够快
- 并发 30 的混合查询已经很稳
- 当前最大短板是首个冷请求接近 `1 秒`

所以接下来应该优先解决“冷”，不是优先解决“搜”。

## 3. 现在要不要继续补 ES 查询预热

我的建议是：

`先不把 ES 作为当前主线任务。`

更准确地说：

- `现在不需要为了筛选性能立刻补 ES`
- `可以把 ES 放到下一阶段，专门服务搜索框和模糊搜索`

原因：

1. 目前慢的不是热筛选，而是冷启动。
2. 结构化筛选本身更适合 PostgreSQL。
3. 现在就上 ES，会先增加部署复杂度、同步成本和资源压力。
4. 在你还没有把热点预热、慢查询监控、索引命中情况跑清楚之前，上 ES 的收益不会最大。

换句话说：

当前顺序应该是：

1. `先做压测常态化`
2. `再做冷启动预热`
3. `再做 SQL 慢查询观测`
4. `最后再决定是否补 ES 搜索层`

---

## 4. 下一步最应该补的内容

## 4.1 第一优先级

### A. 热点查询预热

你现在已经把热点查询写进 Redis 排行里了，所以最自然的下一步就是：

- 服务启动后自动读取 `admission:hot-query-ranking`
- 取 Top N 热门查询
- 自动回源一次，提前把结果写热

这样可以直接压低首个冷请求时间。

### B. 慢查询看板

建议把这些指标拉出来：

- 接口总耗时
- SQL 查询耗时
- Redis 命中率
- 页面 1 查询命中率
- 最慢 Top 10 查询条件

这一步做完后，你就不会靠感觉判断要不要上 ES，而是可以直接看数据。

### C. 放榜前定时预热

如果查分高峰是可预期的，建议在高峰前用定时任务把常见条件提前预热，例如：

- 云南 + 物理组 + 常见分数段
- 云南 + 历史组 + 常见分数段
- 本科 / 专科
- 公办 / 民办
- 冲 / 稳 / 保

这对“放榜时第一波用户”很有帮助。

---

## 4.2 第二优先级

### A. SQL 慢查询定位

建议重点观察这些是否是慢点：

- 分数区间判断
- 风险桶计算
- 关键词过滤
- 排序字段是否命中索引

如果慢查询主要集中在 SQL 结构本身，那应该先改 SQL 或索引，而不是先补 ES。

### B. 分页与返回字段继续收紧

要继续坚持两件事：

- 只查列表页真的需要的字段
- 所有列表必须分页，不能回到整包拉取

这是后端筛选版能一直稳住的基础。

## 5. 2C4G 现在够不够

### 如果 2C4G 一台机同时跑这些

- Node API
- PostgreSQL
- Redis
- Elasticsearch

那这个规格偏小，不建议作为生产方案。

### 如果 2C4G 只跑应用层

前提是：

- PostgreSQL 独立
- Redis 独立

那么它可以作为早期生产或测试环境继续用，但不适合你设想的“高峰很多人一起查”。

### 对你当前阶段的实际判断

如果你现在还没有正式把 ES 上线，那 `2C4G` 先跑：

- `Node + PostgreSQL + Redis`

会比：

- `Node + PostgreSQL + Redis + Elasticsearch`

更稳，也更符合当前压测结论。

---

## 6. Elasticsearch 大概会吃多少资源

如果 ES 只用来做：

- 学校名搜索
- 专业名搜索
- 搜索建议词
- 简单模糊搜索

并且文档量只是几万到几十万规模，实战上通常也要预留：

- JVM Heap：`1GB ~ 2GB`
- 额外进程与系统缓存：`1GB ~ 2GB`

也就是说：

`单节点 ES 通常就会比较舒服地占掉 2GB ~ 4GB 内存`

所以你现在这台 `2C4G`：

- 能勉强起一个小 ES 做开发测试
- 不适合作为 Node + PG + Redis + ES 同机生产部署

---

## 7. 我对服务器规格的建议

### 当前阶段最推荐

- 应用机：`2C4G` 或 `4C8G`
- PostgreSQL：独立实例，至少 `2C4G`
- Redis：独立实例，至少 `1C2G`
- `先不上 ES 主流程`

### 如果下一阶段要补 ES

- 应用机：`4C8G`
- PostgreSQL：`4C8G`
- Redis：`2C4G`
- Elasticsearch：`4C8G`

如果预算紧张，ES 也最好单独放，不建议和数据库挤在一起。

---

## 8. 对“10 万用户、1 万人同时查询”的最终判断

这套方案方向上是合适的，但前提是：

1. 热点查询命中率高
2. 后端多实例部署
3. PostgreSQL 和 Redis 独立
4. 有预热、有监控、有分页、有降级

如果只靠单机 `2C4G`，哪怕补上 ES，也不够稳。

真正决定能不能扛住高峰的核心不是“有没有 ES”，而是：

- `热点命中率`
- `数据库扛压能力`
- `应用层实例数`
- `冷启动是否被预热掉`

---

## 9. 这轮结果对应的行动顺序

建议按这个顺序推进：

1. 保持当前 `后端筛选 + Redis 热点缓存` 为主方案。
2. 新增 `热点查询启动预热`。
3. 新增 `真实接口压测脚本固定化`。
4. 新增 `慢查询看板 / Redis 命中率看板`。
5. 根据一轮真实高峰数据，再决定是否补 `Elasticsearch 搜索层`。

如果只看当前压测结果，我的判断是：

`现在先不用急着补 ES 查询预热，先把 PostgreSQL + Redis 这条主链路打磨完整，收益最大。`
