# 2026-05-28 后端筛选版真实接口压测与慢查询看板

## 1. 本次测试结论

这轮结果已经足够说明一个关键点：

`后端筛选 + Redis 热缓存` 这条路线是成立的，而且在热点命中后，接口响应已经明显快于“前端整包拉取再本地筛选”。

本次最关键的几个数字：

- 首个冷请求：`1184.7ms`
- 热缓存后，基础大列表单次查询：`7.15ms`
- 热缓存后，带 `score + riskBucket + schoolLevel + ownershipType` 的单次查询：`104.78ms`
- 热缓存后，窄条件关键词查询单次：`64.68ms`
- 混合查询并发 30：`P95 = 34.28ms`，`P99 = 37.95ms`，`错误率 = 0`

所以现阶段的判断很明确：

1. `不需要因为筛选性能马上补 Elasticsearch`
2. `要先把 Redis 热点预热和缓存保温做好`
3. `真正需要重点处理的是冷启动首包慢`

## 5. 冷请求结果

冷请求只记录了服务重启后第一条真实筛选请求：

| 场景 | 耗时 |
| --- | --- |
| A 基础大列表 | `1184.7ms` |

结论：

- 首包冷请求已经接近你关心的 `1 秒` 边界，略高一点。
- 这说明系统真正的短板不是热查询，而是：
  - 首次 SQL 聚合
  - 首次缓存构建
  - 首次数据序列化

这也是为什么我建议你下一步重点做：

1. 热点查询预热
2. 服务启动后自动 warm-up
3. 放榜前定时预热热门条件

## 11. 对 Elasticsearch 的判断

基于这轮结果，我的判断是：

### 现在还不需要因为筛选性能补 ES

原因：

1. 热请求已经非常快。
2. 混合并发下 P95 也很低。
3. 当前主要瓶颈是冷启动，不是热点筛选。

### 如果补 ES，优先用途仍然应该是搜索增强

适合交给 ES 的还是这些：

- 学校名模糊搜索
- 专业名模糊搜索
- 联想词
- 拼写不完整搜索

不建议为了当前筛选性能把主链路直接迁到 ES。

---

## 12. 下一步建议

按优先级排序，我建议你接下来这样做：

### 第一优先级

做缓存预热。

重点：

1. 服务启动后，预热 Top 10 热门筛选
2. 每 10 分钟刷新一次热门筛选缓存
3. 放榜高峰前手动预热

### 第二优先级

补数据库侧慢查询观测。

建议启用：

- `pg_stat_statements`
- `auto_explain`
- 慢 SQL 阈值日志

这样下一轮“慢查询看板”就能从接口层下钻到 SQL 层。

### 第三优先级

压测生产相近部署规格。

因为本轮是本地开发环境，下一步最好在你计划的服务器规格上复测：

- `2C4G`
- `4C8G`
- Redis 独立 / 不独立

这样才能判断真实上线抗压边界。
