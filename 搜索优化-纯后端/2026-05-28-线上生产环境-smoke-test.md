## 5. 本次线上 smoke 结论

这轮线上结果可以明确得出几件事：

1. 生产环境的 `后端筛选版 admission 列表接口` 已经正常工作。
2. 登录后真实筛选、风险桶筛选、关键词筛选都能返回正确结果。
3. 线上主要瓶颈依然是 `首个大列表冷请求`。
4. 一旦进入热状态，请求基本可以回到 `80ms ~ 100ms` 区间。

最关键的一条判断是：

`线上当前不是“热查询慢”，而是“首包冷查询偏慢”。`

## 6. 对下一步的建议

基于这次线上 smoke，下一步优先级建议如下：

1. 先补 `热点查询启动预热`
2. 再补 `线上慢查询看板`
3. 再补 `Redis 命中率 / 热点命中率观察`
4. 暂时不要为了这个问题优先把主筛选链路切到 ES

原因很简单：

- 如果把首个热点大列表提前预热掉，当前线上最明显的 `1.7s` 问题就有机会直接下降很多
- 现在热请求已经不慢，贸然上 ES 的收益不会比“先做预热和观测”更大

## 7. 风险提示

这轮是 `smoke test`，不是正式压测，因此有两个边界：

1. 它说明“线上功能链路可用 + 响应时间大致落点”
2. 它不能直接代表“高峰并发下的最终表现”

如果要进一步判断生产可承载能力，建议下一步补：

- 线上只读低并发 RT 采样
- 应用日志中的慢请求分布
- 数据库慢 SQL 排行
- Redis 命中率统计

这样你就能判断：

- 是不是只要做预热就够
- 还是确实需要继续上更重的搜索增强层
