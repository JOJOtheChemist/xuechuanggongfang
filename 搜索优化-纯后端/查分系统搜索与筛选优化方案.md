# 查分系统搜索与筛选优化方案

## 1. 先说结论

对于你现在这个查分 / 志愿系统，最合适的主方案不是一上来就把所有筛选都交给 Elasticsearch，而是：

`前端只传筛选条件 -> 后端做查询 -> PostgreSQL 负责结构化筛选 -> Redis 缓存热门结果 -> 关键词搜索再按需补 Elasticsearch`

如果你的目标是：

- 用户主要在查 `分数 / 位次 / 省份 / 城市 / 院校层次 / 公办民办 / 专业类别 / 冲稳保`
- 希望大多数请求 `1 秒内返回`
- 数据规模目前还没有到百万级、千万级

那么最优先的路线是：

1. 把筛选全部收回后端。
2. 用 PostgreSQL 扛结构化查询。
3. 用 Redis 缓存热门查询和热门详情。
4. 把 Elasticsearch 只用于关键词搜索、联想搜索、模糊搜索，不让它承担整套核心业务筛选。

这套方案比“全部交给前端筛选”稳定得多，也比“所有东西都上 ES”更省资源、更容易落地。

---

## 2. 结合你当前项目的现状判断

你当前后端已经具备比较好的基础：

- 技术栈是 `Node.js + Express + PostgreSQL + Redis`
- 查分 / 志愿这块已经做了本地内存缓存 + Redis 缓存
- 列表、详情、全量快照都已经有缓存逻辑
- `admission / gaokao` 相关表已经建了常用索引

说明你现在不是从 0 开始，实际上已经走在“纯后端查询 + 缓存”这条路上了。

所以你的优化重点，不应该是“要不要前端筛选”，而应该变成：

1. 哪些条件必须由 SQL 直接过滤。
2. 哪些结果应该进 Redis。
3. 哪些查询要预热。
4. 哪些关键词搜索值得单独交给 Elasticsearch。

---

## 3. 推荐架构

## 3.1 主链路

推荐把接口拆成两类：

### A. 结构化筛选接口

适合条件：

- 省份
- 城市
- 学校层次
- 公办 / 民办
- 专业类别
- 考试类型
- 分数
- 位次
- 冲 / 稳 / 保

执行方式：

- 由 PostgreSQL 直接查询
- 严格分页
- 只返回列表页需要的字段
- Redis 缓存热门组合结果

### B. 搜索接口

适合条件：

- 学校名关键词
- 专业名关键词
- 模糊搜索
- 联想词
- 拼写不完整

执行方式：

- 初期：PostgreSQL `ILIKE + pg_trgm`
- 后期：如果搜索体验要求更高，再补 Elasticsearch

也就是说：

- `筛选` 主要靠数据库
- `搜索` 才考虑搜索引擎

不要把这两种需求混成一个东西。

---

## 3.2 Redis 应该怎么用

Redis 最适合做的是“结果缓存”，不是“主查询引擎”。

推荐缓存这些内容：

1. 热门筛选结果
例如：

- 云南 + 物理组 + 500 分 + 本科 + 公办
- 云南 + 历史组 + 460 分 + 专科 + 稳

2. 热门学校详情

3. 首页默认推荐

4. 某些整包快照
例如：

- 某考试类型下的学校列表快照
- 某大类专业列表快照

### Redis Key 建议

可以按这种思路：

```text
admission:list:{hash(filters)}
admission:detail:{institutionId}:{hash(filters)}
admission:snapshot:{hash(filters)}
admission:search:suggest:{keyword}
```

### TTL 建议

- 列表缓存：`5 ~ 15 分钟`
- 详情缓存：`10 ~ 30 分钟`
- 快照缓存：`1 ~ 12 小时`
- 联想词缓存：`30 ~ 60 分钟`

### 注意

不要把所有组合条件都提前写进 Redis。

因为组合一多会爆炸。正确做法是：

- 查询先查 Redis
- 没命中再查 PostgreSQL
- 查到后按规则回填 Redis

---

## 3.3 Elasticsearch 应该放在哪

Elasticsearch 适合做下面这些：

1. 学校名模糊搜索
2. 专业名模糊搜索
3. 联想搜索
4. 多字段综合搜索
5. 搜索结果相关性排序

Elasticsearch 不适合直接替代你全部业务查询逻辑，原因是：

1. 结构化筛选本来 PostgreSQL 就很强。
2. 你的核心数据是强业务关系数据，不是纯文档搜索。
3. ES 维护成本、资源成本、同步成本都比 PostgreSQL 高。

所以最合理的方式是：

- PostgreSQL 作为主数据源
- Redis 作为热点缓存
- Elasticsearch 作为“搜索增强层”

而不是：

- Elasticsearch 作为唯一查询核心

---

## 4. 10 万用户、1 万人同时查询，这个方案是否合适

## 4.1 先给直接结论

`合适，但有前提。`

如果你的意思是：

- 总用户量 10 万
- 高峰时刻 1 万人几乎同时点查询

那么：

- `PostgreSQL + Redis + 后端分页 + 热门缓存` 这条路线本身是对的
- 但 `单机 2C4G` 顶不住这样的真实高峰
- 即使补上 Elasticsearch，`2C4G` 也仍然不够

真正决定能不能扛住的，不是“有没有 ES”，而是：

1. 热门查询命中 Redis 的比例有多高
2. 同时请求到底是热点相似查询，还是 1 万个完全不同的冷查询
3. 你的数据库、应用、Redis、ES 是不是分机器或分实例部署
4. 是否有分页、限流、连接池、异步预热

---

## 4.2 这套方案在高并发下什么时候可行

### 可行场景

如果高峰期大量用户查的是相似条件，例如：

- 同一个省
- 分数集中在几个常见分段
- 常见学校和专业查询很多重复

那么 Redis 热缓存命中率会比较高，这时方案很合适。

因为高频请求会变成：

`请求 -> Redis 命中 -> 直接返回`

这种场景下，接口延迟可以压得很低。

### 不可行场景

如果 1 万并发里大多数都是完全不同的复杂查询，而且都没缓存命中，那么会发生：

- 大量请求同时打 PostgreSQL
- SQL 聚合、排序、EXISTS 子查询压力变大
- 连接池打满
- Node 进程排队
- 接口 RT 快速上升

也就是说：

`1 万同时查询不等于 1 万 QPS 一定可扛`

这个方案能扛住高峰，但前提是：

- 热点缓存命中率高
- 分页严格
- SQL 索引合理
- 应用和数据库不是塞在一台小机器里

---

## 4.3 我对“10 万用户 / 1 万并发”的建议判断

### 如果你是中早期产品

推荐先做：

- PostgreSQL 主查询
- Redis 热缓存
- 不上 Elasticsearch，或只给搜索框单独上 ES
- 把高频条件做缓存预热

这时足够支持：

- 总用户量 10 万
- 日常查询高峰
- 中等规模并发

### 如果你真的要面对“高峰 1 万同时点查询”

建议进入增强版架构：

1. API 多实例部署
2. Redis 独立实例
3. PostgreSQL 独立实例
4. Elasticsearch 只服务搜索接口
5. 热点查询预热
6. 接口限流与降级
7. 复杂详情查询和搜索分开

换句话说：

`10 万用户` 没问题，`1 万同时查询` 不是功能问题，而是部署规格和流量治理问题。

---

## 5. Elasticsearch 要不要补

我的建议是：

### 结论

`要补，但只补搜索，不补整套结构化筛选。`

### 适合给 ES 的功能

1. 学校名搜索
2. 专业名搜索
3. 搜索建议词
4. 拼音 / 简拼 / 模糊匹配
5. 搜索排序

### 不建议给 ES 的功能

1. 冲稳保完整判定
2. 分数线统计均值
3. 复杂业务权限判断
4. 全套详情页拼装
5. 强事务一致性逻辑

更直白地说：

- `学校 / 专业搜索框` 可以交给 ES
- `查分筛选主流程` 还是交给 PostgreSQL

---

## 6. Elasticsearch 大概占多少内存

这里给你的是实战估算，不是理论最小值。

## 6.1 小规模单节点 ES

如果只是存：

- 学校
- 专业
- 搜索建议词
- 少量结构化字段

文档量在几万到几十万以内，单节点 ES 一般建议：

- JVM Heap：`1GB ~ 2GB`
- 进程额外开销 + OS Page Cache：`1GB ~ 2GB`

也就是说：

`ES 单独就比较舒服地吃掉 2GB ~ 4GB 内存`

这还是“小规模、单节点、搜索功能为主”的估算。

---

## 6.2 为什么 ES 不只是看 Heap

很多人以为给 ES 配 `1GB heap` 就只占 1GB，这是不对的。

ES 实际内存消耗通常包括：

1. JVM Heap
2. JVM 自身额外内存
3. Lucene 段文件缓存
4. 操作系统页缓存
5. 查询聚合临时开销

所以你看到的真实占用，往往会明显大于 heap。

---

## 6.3 你这个业务大概怎么估

如果 ES 只存搜索索引，比如：

- 院校名称
- 专业名称
- 地区
- 学校层次
- 专业类别
- 若干搜索辅助字段

这种量级其实不算大，磁盘不会太夸张，真正敏感的是内存和 CPU。

我的经验判断：

- 开发 / 测试：`2C4G` 勉强能跑一个很小的 ES，但非常紧
- 生产小流量：`4C8G` 才开始比较像样
- 生产中等流量：`8C16G` 更稳妥

---

## 7. 你现在 2C4G 是否太小

## 7.1 如果是单机同时跑这些

如果你一台服务器同时跑：

- Node 后端
- PostgreSQL
- Redis
- Elasticsearch

那 `2C4G` 明显偏小，不建议这样上生产。

原因很简单：

- PostgreSQL 要内存
- Redis 要内存
- Node 高并发要内存
- Elasticsearch 也要内存

4GB 很快就被挤满，最后会出现：

- 频繁 GC
- 响应时间抖动
- OOM 风险
- 磁盘 swap
- ES 和 PG 互相抢资源

### 结论

`2C4G 不适合单机同时承载 Node + PG + Redis + ES 的生产流量。`

---

## 7.2 如果 2C4G 只跑应用层

如果你的 PostgreSQL 和 Redis 是独立服务，2C4G 只跑：

- Node API
- 少量本地缓存

那么 2C4G 可以作为小流量早期生产或测试环境。

但如果你说的是高峰期接近 1 万同时查询，还是不够。

---

## 8. 我建议的服务器规格

## 8.1 最省钱起步版

适合：

- 产品早期
- 总用户 10 万以内
- 并发不算特别高
- 先把主流程跑稳

建议：

- 应用机：`2C4G` 或 `4C8G`
- PostgreSQL：独立实例，至少 `2C4G`
- Redis：独立实例，至少 `1C2G`
- 暂时不上 ES，搜索先用 PostgreSQL `pg_trgm`

这是最推荐的第一阶段。

---

## 8.2 中期推荐版

适合：

- 查分高峰明显
- 搜索需求开始增强
- 想补 Elasticsearch

建议：

- 应用机：`4C8G`
- PostgreSQL：`4C8G`
- Redis：`2C4G`
- Elasticsearch：`4C8G`

如果预算有限，ES 可以先单节点。

这时：

- 主筛选走 PG
- 热门结果走 Redis
- 搜索框走 ES

这会比“全塞一台机器”稳定很多。

---

## 8.3 高峰更稳妥版

适合：

- 明确有大促式 / 放榜式高峰
- 真的可能出现大量同时查询

建议：

- API 应用层：至少 `2 台 4C8G` 做负载均衡
- PostgreSQL：`4C8G` 起步，最好更高
- Redis：`2C4G` 或更高
- Elasticsearch：`8C16G` 更稳

如果预算允许，数据库和搜索建议走托管服务或云实例。

---

## 9. 分阶段落地建议

## 第一阶段：先不用 ES 扛主流程

目标：

- 把“前端筛选卡顿”问题立刻解决
- 让绝大部分请求先能稳定在 1 秒左右

执行：

1. 所有筛选后移到后端。
2. 列表严格分页。
3. SQL 只查必要字段。
4. 热门查询结果写 Redis。
5. 热门条件做缓存预热。
6. 补齐慢查询日志和接口耗时监控。

---

## 第二阶段：补 Elasticsearch

目标：

- 提升搜索框体验
- 支持模糊搜索 / 联想搜索

执行：

1. 只把学校 / 专业搜索索引同步到 ES。
2. 搜索接口改成先查 ES。
3. 详情和筛选主流程仍走 PostgreSQL。
4. 搜索结果只返回 ID 列表，再回源 PG 补业务字段。

这样做的好处是：

- ES 压力可控
- 业务一致性更容易保证
- 不会把整套筛选逻辑搬进 ES

---

## 第三阶段：应对高峰并发

目标：

- 放榜高峰时不崩

执行：

1. API 多实例
2. Redis 独立部署
3. PostgreSQL 独立部署
4. 热点榜单和热门查询预热
5. 搜索与筛选接口拆分
6. 接口限流、熔断、超时控制
7. 对极重接口准备降级返回

---

## 10. 最终建议

如果让我直接替你拍板，我会这样定：

### 方案选择

- 主筛选：`PostgreSQL`
- 热门缓存：`Redis`
- 搜索增强：`Elasticsearch`
- 前端：只负责展示，不做大数据量本地筛选

### 对 10 万用户 / 1 万同时查询的判断

- 架构方向是对的
- 但前提是你不能把所有服务挤在 `2C4G` 上
- `2C4G` 作为开发机或很早期测试机可以
- `2C4G` 作为生产单机承载 `Node + PG + Redis + ES` 不合适

### 我对你机器规格的建议

- 如果暂时不上 ES：尽量至少分成 `应用机` 和 `数据库 / Redis`
- 如果要上 ES：建议最少进入 `4C8G + 独立 PG + 独立 Redis + 独立 ES`
- 如果你真要应对明显高峰：应用层建议至少多实例，ES 也不要和所有服务共机

---

## 11. 一句话版本

`你的查分系统最适合走“纯后端筛选 + PostgreSQL 主查询 + Redis 热缓存 + Elasticsearch 只做搜索增强”的路线；10 万用户可以，1 万同时查询也不是不能做，但 2C4G 单机肯定偏小，尤其加上 Elasticsearch 后更不适合。`
